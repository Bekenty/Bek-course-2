   3. Анализ требований и схема работы (вход → проверка → выход)В соответствии с требованиями безопасности:   Пароли на сервере не хранятся в открытом виде (используется сверка хешей).   Токены сессии не сохраняются в localStorage для снижения рисков при XSS-атаках; используется sessionStorage в связке с серверной проверкой.   Проверка доступа к защищенным ресурсам выполняется сервером при каждом запросе. При невалидной сессии возвращается код HTTP 401 Unauthorized, при нехватке прав или попытке доступа к чужому профилю — HTTP 403 Forbidden.   Схема жизненного цикла сессии:Вход (POST /login): Клиент отправляет логин и пароль → сервер проверяет наличие данных (иначе 400), сверяет учетные данные (иначе 401), генерирует JWT (header.payload.signature), сохраняет активную сессию в памяти сервера и возвращает токен клиенту.   Проверка доступа (GET /profile, защищенные API-маршруты): Клиент передает токен → сервер проверяет подпись JWT, сверяет версию токена пользователя (tokenVersion) и время жизни (exp). Далее проверяется роль пользователя (student / teacher / admin) и принадлежность ресурса.   Выход (POST /logout и POST /logout-all): При обычном выходе сервер удаляет текущую сессию из хранилища. При выходе со всех устройств сервер увеличивает tokenVersion пользователя, делая все ранее выданные токены недействительными.

Описание клиентской и серверной частейПроект реализован в виде автономных гибридных веб-модулей (basic_variant1.html и advanced_variant20.html) на языке JavaScript:   Клиентская часть: Форма авторизации с валидацией ввода, панель личного кабинета, индикатор обратного отсчета времени сессии, кнопки обращения к защищенным маршрутам и журнал событий безопасности (аудит).   Серверная часть (модуль AuthBackend / MockServer): Имитирует работу серверного API, хранит реестр активных сессий (Map), формирует и верифицирует подпись JWT, контролирует время жизни сессии (TTL = 60 секунд) и разграничивает права доступа по ролям.

Дополнительные меры безопасности (Творческое задание)В рамках творческого задания реализованы три механизма повышения безопасности и удобства:   Визуальный индикатор оставшегося времени сессии: пользователь видит точный обратный отсчет до автоматического завершения сессии.   Безопасный выход со всех устройств: реализован через версионирование токенов (tokenVersion) на стороне сервера.   Журнал аудита безопасности: фиксирует в реальном времени все успешные входы, отказы в доступе (401/403) и завершение сессий.   
     8. ВыводВ ходе выполнения лабораторной работы были изучены принципы аутентификации и авторизации, структура токенов JWT и механизмы управления серверными сессиями. На практике подтверждено, что надежная защита веб-приложения невозможна только за счет скрытия элементов интерфейса на клиенте — проверка подписи токена, срока его действия, ролей и принадлежности ресурсов должна обязательно выполняться на стороне сервера.
